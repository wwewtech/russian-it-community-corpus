# ADR 0006: The published dataset contract is declared, versioned and enforced

- **Status**: Accepted
- **Date**: 2026-10-21
- **Deciders**: maintainer
- **Relates to**: `docs/architecture/data-models.md`, `ricc/validation/validator.py`

## Context

The public contract of this project is the **column set** of the exported
Parquet files. A consumer who downloads `full_clean_messages.parquet` and
writes code against `text_clean`, `domain` and `tags` needs to know when one
of those is renamed, removed or retyped.

Nothing carried that information:

- `ricc/validation/artifact_manifest.py` had `SCHEMA_VERSION = 1`, but that
  versions the **manifest format**, not the data — a reader of the code
  could reasonably think otherwise.
- `DatasetValidator.validate_parquet_files` claimed to check "schema
  conformance" but only counted columns (`col_count = table.num_columns`)
  and compared nothing. A renamed column, a reordered column or a retyped
  column all passed silently.
- The Parquet files carried only the `pandas` metadata block, so nothing in
  a downloaded file said which contract it was written against.

`docs/architecture/data-models.md` promised "dtypes pinned by
DatasetValidator", which was not true.

## Decision

Declare the contract in code, version it, write it into the artefacts and
enforce it.

1. **`ricc/schema_version.py` is the declaration.** It lists, for every
   exported artefact, the column names, their **order** and their Arrow
   types. The values were taken from the published files and are verified
   against them by a test, so the declaration cannot drift away from the
   data unnoticed.

2. **A version and a fingerprint.** `DATASET_SCHEMA_VERSION` is semver:
   MAJOR when a column is removed or retyped (a breaking change for a
   consumer), MINOR when a column is added, PATCH for documentation. The
   `schema_fingerprint()` hashes the whole contract, so a change to any
   column of any artefact is detectable even when the version was not
   bumped.

3. **The version travels with the data.** The exporter writes the version
   and the fingerprint into the Parquet key-value metadata, next to the
   existing `pandas` block, so a downloaded file says which contract it was
   written against.

4. **The validator enforces it.** The column names, their order and their
   types must match the declaration, and the version metadata must be
   present and current. A mismatch fails the validation with the status
   `INVALID` and a list of the problems — it is not logged and ignored.

5. **A machine-readable manifest.** `reports/dataset_schema.json` records
   the version, the fingerprint and the full contract. It is generated by
   `scripts/generate_schema_manifest.py` (with a `--check` mode wired into
   CI) and is derived from the code, never hand-maintained.

### Why the JSONL exports are versioned differently

The JSONL exports are declared in the contract as well, with their record
shape, but their version travels in the contract manifest rather than in
the files. A header line would be the natural in-band choice, but the
JSONL validator counts **valid lines**, and the consumers rely on
"every line is a record". A header would break that contract for every
downstream reader. The sidecar manifest carries the same information
without touching the data files.

## Consequences

- A consumer can verify what they downloaded: the fingerprint in the file
  must match the one in the manifest for the release they expect.
- A column rename is now a **validation failure**, not a silent change that
  surfaces weeks later in somebody's notebook.
- The published files on the Hub predate the versioning, so they carry no
  version metadata and the validator reports that gap. They are correct
  against the declared contract (names, order and types) — only the
  metadata is missing. Re-exporting them adds it.
- Adding a column is a MINOR bump and does not break a consumer that
  ignores it; removing or retyping one is MAJOR and must be called out in
  the changelog.

## Alternatives rejected

- **Rely on the file name.** The names already carry the version
  (`sft_dialogues.parquet`), but a name cannot describe a column set.
- **Version only the manifest.** The manifest is downloaded separately from
  the data, so the pairing between "this file" and "this contract" would
  rely on the consumer doing the bookkeeping.
- **A separate `schema.json` next to every Parquet file.** More files to
  keep in sync, and the metadata is already the place Arrow keeps
  file-level information.
